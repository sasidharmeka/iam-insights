01 / THE ESSENTIAL IDEA

Security data is abundant.
Understanding takes work.

An identity investigation spans logins, access grants, application activity, and lifecycle events. A useful answer needs those signals connected—and its reasoning tied to evidence.

This project connects a synthetic IAM data pipeline to a conversational analyst. The model interprets the question. Governed tools retrieve the evidence. An evaluation layer checks how the system behaved.

    BENCHMARK DESIGN / SOURCE-VERIFIED

    What the 132 cases actually test.

    The published benchmark file contains 132 defined cases, not 132 independently labeled factual answers. It includes 88 catalog-coverage cases (repeated patterns spanning registered analytical concepts), 20 identity/entity-scope cases, 10 general IAM explanation cases, 9 authorization-denial cases, 3 additional analytics cases, 1 typo case, and 1 follow-up case.

    Assertions cover expected workflow stages and, where specified, data intent, catalog concepts, target identities, and access denial. Only the 10 general IAM questions include written reference answers in the benchmark definitions. Analytical cases principally test the system's route to evidence; they do not independently establish that every returned numerical fact is correct. The live trajectory runner invokes the actual orchestrator, Gemini, MCP boundary, and configured BigQuery dataset; separate component tests simulate providers.

    These cases provide meaningful regression coverage of the application's defined workflows and safety boundaries, but repeated catalog patterns should not be interpreted as 132 independent natural-language reasoning challenges. Inspect the benchmark definitions ↗ and evaluation methodology ↗.

    01 / GOVERNED QUERY

    Inspect the execution boundary

    Gemini proposes a typed semantic plan; deterministic code validates identity scope, evidence coverage, and query limits before compiling parameterized SELECT statements. In-process MCP is a protocol contract, not separate process isolation.

    SQL compiler ↗ · Validator ↗ · Semantic catalog ↗

    02 / ANALYTICS

    Risk scores are rule-based

    BigQuery risk scores are weighted summaries of correlated IAM detection findings, accompanied by contributing risk factors. They are not trained machine-learning predictions or calibrated probabilities of compromise. The catalog also defines group churn, MFA, and access anomaly outputs.

    Risk-score catalog ↗ · Earlier pipeline source ↗

    03 / EVALUATION

    Behavior checks ≠ accuracy

    The historical 13 October 2026 benchmark passed 129 of 132 specified behavioral cases. Source definitions include 88 catalog-coverage, 20 entity-scope, 10 general, 9 authorization, 3 analytics, 1 typo and 1 follow-up case. Only the 10 general cases provide written reference answers. This is meaningful workflow/regression coverage, not a measurement of 97.7% factual answer accuracy. Gemini judging is not an independent factual oracle; no completed human reviews were recorded in the cited exports.

    Expose catalog discovery and governed query tools.

    Authorize and validate plans, then build parameterized SELECT statements.

    ReportLab · openpyxl · python-docx · python-pptx

    05 / ENGINEERING DECISIONS

    The depth lives
    in the tradeoffs.

    Explore the choices that connect security,
    data engineering, and AI behavior.

    01

    Let the model plan. Let code build SQL.

    +

    Gemini produces a typed semantic plan using the approved catalog. Deterministic code checks scope, concepts, fields, filters, evidence coverage, and resource limits before compiling parameterized SELECT statements.

    THE TRADEOFF

    Constrained analytical building blocks reduce flexibility. In exchange, the system can reject unsupported requests and inspect the boundary before a query executes.

    Inspect the SQL compiler ↗
    02

    Use MCP as an explicit evidence contract.

    +

    The official MCP Python SDK connects an in-process client and server. Catalog discovery and query execution have explicit tool contracts, even though they share a Cloud Run container.

    THE TRADEOFF

    This keeps deployment simpler while preserving a protocol boundary. It does not provide the process isolation of a separate service.

    Inspect the MCP service ↗
    03

    Keep an analysis attached to its evidence.

    +

    Saved results connect the question, plan, response, evidence, and report references to a user and conversation. An export of an existing result uses that result rather than silently performing a new investigation.

    THE TRADEOFF

    Conversation records and report files have separate storage lifecycles. Configured Cloud Storage retains reports across service restarts; in-memory fallback storage does not provide that durability.

    Inspect saved results ↗
    04

    Make delivery authorization explicit.

    +

    The model helps draft a message. A user can edit the recipient, text, and attachments. Preview freezes the reviewed content, and a separate confirmed Send action checks identity and ownership.

    THE TRADEOFF

    Manual mail uses preview and confirmed Send. Newer automation code also supports recurring delivery authorized when the automation is saved, after a one-time Gmail connection. Each run rechecks access; delivery status is recorded separately from analysis success. The supplied successful run was manually triggered.

    EVIDENCE & LIMITATIONS

    What the evidence
    does—and doesn’t—say.

    This showcase explains the implemented architecture. Interactive examples illustrate intended behavior; they do not execute Gemini or BigQuery.

    Recorded release evidence

    The supplied full benchmark and smoke exports were created on 13 October 2026 against revision 133c3074c5b38a719359b6b59b8daa8891d3d201, using Gemini 2.5 Flash with judging enabled and dataset iam_data_dev. Their embedded run IDs, benchmark digests and metrics are preserved in the downloadable curated summary.

    The full benchmark records 129 passes across 132 cases, including two plan-rejection errors and one intent/trajectory failure. Both runs await human review. Application screenshots were captured on 23–24 October; they do not establish that the currently serving code matches the benchmark revision.

    The history screenshot shows a 142-case component run completed. Completion alone is not evidence that every component test passed; no detailed component export was supplied.

    Known limitations

    • General questions can trigger unnecessary data queries. The documented stale-access routing problem is not claimed fixed.
    • Most analytical benchmark cases check behavior rather than independent expected SQL results or exact data answers; no baseline or ablation is reported.
    • Weighted rule-based risk scores are not calibrated predictions or independently validated detector accuracy.
    • The newer IAM_NEW_1 pipeline source was inaccessible during this review; the earlier public pipeline repository is labeled separately.
    • Model judging uses supplied evidence and can overrate answers containing irrelevant material.
    • Historical data, empty results, and missing explanatory fields limit supported conclusions.
    • Synthetic data cannot establish performance in a real enterprise deployment.
    • Code, model behavior, configuration, and data changes can all affect repeated runs.

    Historical benchmark success rates are not current-release accuracy scores. A database snapshot, matching deployed revision and completed human review are still needed for a reproducible release baseline.
